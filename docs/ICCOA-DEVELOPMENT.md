# Independent ICCOA Carlink backend

FT has an experimental phone-side ICCOA implementation in `app.ft.iccoa`. It uses its own Bluetooth handshake, Wi-Fi session, authentication, control framing and WFD media connection. It shares FT rendering, screen encoding, audio capture and car UI components with the other transports.

This is an implementation for testing with a real receiver. Building the APK and passing protocol tests do not establish compatibility with a particular vehicle. A tester tried FT builds 133 and 134 on a Toyota XA60 with a OnePlus 12 Global. Build 134 advanced through PIN submission and received the car's Wi-Fi parameters, then Android rejected the network request with `SecurityException`. The user reports that XiaoDroidLink connects to an XA60; that is useful evidence for choosing the protocol, not a successful end-to-end FT test.

## Backend selection and isolation

`CarProtocol` is a stable saved preference; an absent or unknown value selects CarLife. `CarConnection` dispatches the app switch, automatic start and protocol changes. Changing the selected protocol closes the old connection before starting the new backend.

`IccoaService` owns the ICCOA foreground notification, connection state, session and media lifetime. `IccoaDiscovery` handles bounded BLE discovery and optional GATT service inspection. `IccoaSession` handles the selected car connection and authenticated control lanes. No ICCOA wire messages, authentication state or sockets are placed in `CarLifeService` or `CarLifeSession`.

The inherited `CarIccoaBle` helper and its car-AP handover have been removed from CarLife. Selecting CarLife no longer scans the ICCOA GATT service, accepts its Wi-Fi offers or binds the process to that network. CarLife retains its Bluetooth/RFCOMM and Wi-Fi Direct setup, hotspot and USB transports; ICCOA BLE discovery and car-AP setup belong to the selected ICCOA backend.

`CarControls` exposes transport-independent UI actions and screen state. `IccoaProjection` implements that backend for ICCOA and uses shared `CarDisplay`, `SurfaceEncoder`, `AudioCapture` and `CarTouch` components. Existing CarLife rendering consumes the same shared components through its own adapter. CarLife entry points reject late start intents when ICCOA is selected.

## Connection and media

- The phone scans nearby BLE advertisements and the user explicitly selects a car. The scan is bounded to 60 seconds and 128 devices; up to eight distinct advertisement payloads per device are retained for diagnostics. A UUID or name hint is not a compatibility guarantee.
- The ICCOA implementation uses the Carlink GATT service `2abcc850-9935-4f8a-ba84-123456789100` and its characteristics to exchange connection parameters. The reference also advertises the short service UUID `FCFB`. Discovery remains broad enough to help diagnose receiver variants.
- The supported Wi-Fi path connects the phone to the access point supplied by the car, using Android `WifiNetworkSpecifier`. Android controls the user confirmation dialog. The app keeps traffic on the returned `Network`; it does not assume that the car network becomes Android's default internet network.
- Normal authentication uses the six-digit code displayed by the receiver. P-256 identity/agreement keys, PIN authentication, agreement signatures and derived AES-GCM session keys are scoped to a connection. PINs and session keys are not written to diagnostics or a persistent fast-connect cache. Invalid authentication results fail the connection.
- ICCOA control framing, bounded protobuf parsing, header CRC, session encryption and heartbeat handling are implemented separately from CarLife.
- Before authentication confirmation advertises readiness, the phone opens the WFD RTSP listener on TCP 7236 and the input listener on TCP 4321. RTSP negotiates the receiver's display parameters and RTP/TCP port.
- `IccoaTsMuxer` packages the H.264 stream as MPEG-TS/RTP with RFC 4571 TCP framing. The sender uses a bounded queue and requests a fresh keyframe when frames have to be discarded. Media sockets and blocked writes are bounded by timeouts.
- UIBC input is parsed across TCP records, with bounded JSON/encrypted records and session decryption. Touch and key events go through the ICCOA projection backend to FT's shared UI and phone-control components.
- Capturing phone content or playback audio uses Android's own consent flow. The foreground service is promoted to the media-projection type before a granted projection is used.

### XA60 report and build 134

The supplied build-133 logs show a successful GATT connection at 14:35:16, MTU negotiation and service discovery at 14:35:17, followed by local notification routing for `SERVER_INFO`. There is no subsequent PIN/client-info exchange before FT's Bluetooth watchdog closes the attempt at 14:35:36. The FT bootstrap waited for an extra CCCD descriptor-write callback before requesting the PIN; the inspected XiaoDroidLink 7.62 exchange proceeds directly from local notification routing to PIN entry/client-info writing. The logs identify the waiting stage, but do not establish why the Android/receiver descriptor operation did not complete.

Build 134 follows that observed bootstrap sequence without the extra descriptor write. It also stops the initial Bluetooth watchdog once the ICCOA characteristics are ready: `pinReady` becomes false during PIN submission and is not a valid completion flag for that watchdog. Diagnostics record GATT connection, MTU, service discovery, characteristic-write results and incoming fragment sizes, without recording PINs or Wi-Fi credentials.

### XA60 authenticated-session report and build 138

The build-137 report reaches `receiver-result=0`, successful PIN-MAC and agreement-signature verification, and session-key derivation at 15:53:02.177–178. Diagnostics record lane connections, frame metadata (at most 12 non-heartbeat frames per connection), clean EOF with received-frame counts, and readiness for another connection; payloads and credentials are excluded.

Socket regression checks simulate the XA60's possible immediate auxiliary close, then receive an encrypted control message and an encrypted message on a replacement auxiliary connection. Further checks cover EOF after complete frames, essential-control EOF, truncated auxiliary frames, CRC and GCM failures, and cancellation during accept/read. - **Physical receiver testing:** build 138 reaches WFD PLAY, encoder startup and virtual-display creation on XA60. Visible video, sustained streaming, audio routing and touch coordinate behavior still need a physical test. Independent protocol/unit checks and a successful build cannot substitute for this.

### XA60 WFD PLAY report and build 139

The build-138 report reaches successful authentication at 16:06:59.039–050. The auxiliary lane on 57249 receives one complete frame and closes cleanly at 16:06:59.282; the new listener keeps the session alive. RTSP reaches `WFD PLAY 2422x1272@60; RTP/TCP 15550` at 16:06:59.257. The encoder starts at 16:06:59.410, the virtual display is created at 16:06:59.427 and the presentation is shown at 16:06:59.458. At 16:06:59.495, `Media listener: EOFException` ends the session. These events establish display negotiation and local rendering startup, not visible output on the receiver.

The old shared listener could report that message from either RTSP or UIBC. RTSP handles its read errors internally with an `RTSP:` prefix, so the uncaught EOF points to UIBC on 4321. The report does not distinguish an empty stream, EOF between records and EOF inside a record. The inspected reference treats UIBC closure separately and keeps accepting connections. Build 139 gives UIBC its own session-owned accept loop: EOF before any bytes or after complete records closes only that accepted socket and waits for another connection from the authenticated Wi-Fi peer. A truncated prefix, IV, ciphertext or unfinished JSON object, invalid size or GCM authentication failure remains fatal. Closing FT closes the listener and active socket, including blocked accept/read calls. RTSP lifetime is unchanged.

Diagnostics now name RTSP 7236 and UIBC 4321 independently, record UIBC mode and clean EOF/reconnect readiness, and log the first successfully written video frame without payload contents. A successful socket write alone does not establish that Toyota decoded or displayed the frame. Regression checks use real TCP connections for an unused UIBC close followed by encrypted events on replacement connections, cancellation in accept/read and truncated-input cleanup. Reader checks cover truncation at every encrypted-packet byte boundary, fragmented plaintext JSON, unfinished JSON inside a complete encrypted envelope, invalid authentication tags and oversized records.

Astra's code review identified an additional lifecycle issue: preserving projection after a complete DOWN record followed by EOF would leave an active gesture without its release. Build 139 conservatively treats that EOF as fatal until the projection backends consistently support gesture cancellation. Gesture state is updated only after touch validation; DOWN starts it and UP completes it. MOVE, pointer transitions and the currently unsupported CANCEL do not clear it. Empty streams and streams ending after a completed gesture can reconnect. This avoids changing shared input or CarLife behavior in this fix. The added gesture-state regression check covers these transitions. A second Astra review found the issue resolved and no further blocking findings; this was a code review, not physical receiver validation.

### Build 140: reference compatibility, projection resume and AAC

The independent ICCOA backend now uses the reference's `CLIENT_INFO` compatibility value `manufactures: Xiaomi`, with the real phone model and FT's own persistent six-hex-digit client ID and locally administered unicast MAC. FT does not copy the reference author's device identity. The same persisted ID is used by the current authentication attempt. The Wi-Fi frequency is mapped to a channel, with channel 1 as the unknown-frequency fallback. This is a compatibility profile based on the inspected working XiaoDroidLink implementation; it is not evidence that every ICCOA receiver rejects other manufacturer strings or a Toyota-specific rule.

PAUSE and control methods 5/41 pause and clear media delivery without destroying the car display, phone MediaProjection grant, captured audio or Android Auto session. Repeated PLAY with the same video plan keeps the current screen and requests an IDR after reopening the media queue. Full disconnect still releases all session resources. Queue epochs reject delayed AAC from an earlier paused/overflowed stream, and video resumes only from a current keyframe. Video overflow drops the broken GOP and requests another keyframe; audio overflow drops old audio without discarding video dependencies.

The advertised WFD AAC format is now backed by a MediaCodec AAC-LC encoder at 48 kHz stereo, 192 kbit/s. It consumes FT's PCM16 audio bus and sends raw AAC access units through the existing ADTS/PES/MPEG-TS muxer. A single bounded queue and writer serialize audio and video to the RTP/TCP socket. The PCM sample clock preserves sample precision and never rewinds when captured buffers arrive in bursts; a forward capture gap can rebase it. The earlier control-lane PCM announcement/retry path has been removed from ICCOA. CarLife protocol code is outside these changes.

This build also sends the first encrypted control heartbeat immediately and subsequent heartbeats every two seconds, and reports transport failures with lane/operation context and exception type. Authentication header truncation is attributed to the header-read stage. The PLAY path no longer sends the unrelated mirror-state shutdown command.

Astra reviewed the projection lifecycle and new profile/audio/queue implementation. Two concrete review findings were corrected: RTP socket ownership is published with a closed-state check so cancellation cannot leak a newly created socket, and the AAC sample clock no longer rebases backwards. Regression checks cover burst timestamps, pause/resume epochs, bounded queues, persisted-profile field construction, channel mapping, AAC ADTS/PES framing and advertised AAC negotiation. Android AAC codec behavior, visible projection and sound on the physical receiver remain unverified until the next tester run.

### Build 141: AAC control notifications, repeated RTSP headers and DHCP fallback

Reference comparison confirmed that removing the old PCM announcement also removed a necessary AAC control message. Method 8 now announces the AAC stream using protobuf fields `1=16`, `2=state`, `3=48000`, `4=2`, `6=audio/mp4a-latm`. PLAY requests state 0 for the first start, PAUSE/control 5/41 requests state 2, and a later PLAY requests state 3. Repeated PLAY does not restart an already announced player. If control port 57219 is not open yet, a session-owned retry retains only the latest desired state. Disconnect removes retries and resets the state; the next connection starts afresh. The log describes queue acceptance, not receiver acknowledgement. These are stream lifecycle notifications; automatic switching based on audible PCM activity is not implemented here.

The independent method-24 configuration request is scheduled three seconds after the first successful local PLAY startup, with retry if the control lane is not available. It does not depend on method 8 succeeding. Closing the connection cancels both callbacks. Neither path sends PCM through the control audio lane; AAC media still uses RTP/TCP.

RTSP parsing now combines repeated comma-list fields (`Public`, `Allow`, `Require`, `Proxy-Require`, `Supported`, `Unsupported`) in received order and accepts identical singleton repetitions. Conflicting CSeq, Content-Length, Session and other non-combined fields fail before the body is consumed. Existing header/body limits remain. Alternative Transport proposals are not negotiated by this implementation, so differing repeated Transport fields remain rejected. This follows the list-combination rule in [RTSP 1.0 section 4.2](https://www.rfc-editor.org/rfc/rfc2326.html#section-4.2), which refers to HTTP message-header syntax.

LinkProperties routes remain the primary source of the receiver address. If the IPv4 gateway is absent, FT checks WifiManager DHCP data against the exact IPv4 address and prefix of the requested car Network. Mismatched local addresses, off-subnet, reserved, self, network and broadcast gateways are rejected; no `.1` address is guessed. Android documents that, on concurrent Wi-Fi, [getDhcpInfo](https://developer.android.com/reference/android/net/wifi/WifiManager#getDhcpInfo()) returns the specifier connection to the app that requested it. The fallback is deprecated but useful for compatibility; its data is checked rather than trusted blindly. An unavailable gateway is retried within the existing connection deadline and produces a distinct timeout status. Diagnostics record whether routes or validated DHCP supplied the address, without logging Wi-Fi credentials. Global process binding remains unnecessary: outgoing authentication and RTP sockets retain their individual Network binding.

New regression checks cover delayed AAC control availability, start/pause/resume transitions, replacement of stale pending notifications, reconnect reset, DHCP byte order and subnet/ownership validation, repeated RTSP list fields, conflicting singletons and preservation of the following message boundary. Physical XA60 connection, display and sound still require tester validation; these changes do not prove the cause of the previous control-channel interruption.
