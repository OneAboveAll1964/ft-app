# CarLife: отказ подключения 7 ноября и проверка гипотезы CarPlay

Дата исследования: 9 ноября 2026 года.

## Вывод

Сбой 7 ноября в 11:44 произошёл при формировании Wi-Fi Direct, до TCP-каналов CarLife и Android Auto. В доступном автомобильном SDK не найден отдельный обмен для освобождения CarLife после CarPlay. Причина первого зависания переговоров не установлена.

При сопоставлении SDK с журналом обнаружен дополнительный признак: после отмены неудачной попытки телефон подтверждает отсутствие группы, а автомобиль сразу после ответа с именем запрашивает IP телефона. В изученном SDK такой ответ соответствует ветке, в которой автомобильная сторона уже считает P2P подключённым и не запускает обнаружение заново. Это основание проверить рассинхронизацию состояния сторон, но не доказательство ошибки конкретной прошивки и не подтверждение влияния iPhone.

## Порядок подключения в SDK

В [InstantConnectionSetup.kt](https://github.com/fgrcwp/apollo-DuerOS/blob/fddb0be12a24b501bee435a56be3f564a158fd39/CarLife-Android-Vehicle-V2.0/carlife-sdk/src/main/java/com/baidu/carlife/sdk/receiver/transport/instant/InstantConnectionSetup.kt):

1. `WIRELESS_INFO` сообщает поддерживаемые способы связи: 0 — нет, 1 — Wi-Fi, 2 — Wi-Fi Direct, 3 — оба способа. `type=3` не подтверждает готовность к подключению.
2. На `TARGET_INFO_REQUEST` машина сначала отвечает именем.
3. Затем проверяет `wifiDirectManager.isConnected`. При `true` запрашивает IP телефона. При `false` запускает `discoverable()`.
4. Событие `groupFormed` также запускает запрос IP. Пустой ответ при существующей группе приводит к повтору запроса через секунду.
5. Непустой IP передаётся обработчику подключения TCP.

В [WifiDirectDiscoverableTask.kt](https://github.com/fgrcwp/apollo-DuerOS/blob/fddb0be12a24b501bee435a56be3f564a158fd39/CarLife-Android-Vehicle-V2.0/carlife-sdk/src/main/java/com/baidu/carlife/sdk/receiver/transport/instant/WifiDirectDiscoverableTask.kt) подготовка выполняет `stopPeerDiscovery` → `discoverPeers`; при ошибке повторяет последовательность каждые две секунды. Обязательного предварительного `createGroup` здесь нет. При завершении задачи вызывается `cancelConnect`.

В [WifiDirectManager.kt](https://github.com/fgrcwp/apollo-DuerOS/blob/fddb0be12a24b501bee435a56be3f564a158fd39/CarLife-Android-Vehicle-V2.0/carlife-sdk/src/main/java/com/baidu/carlife/sdk/receiver/transport/instant/WifiDirectManager.kt) признак `isConnected` обновляется по `groupFormed` и состоянию P2P. При разрыве повторное обнаружение запускается с учётом текущего типа соединения. Эти ветки зависят от состояния автомобильного процесса; телефон не может непосредственно сбросить его переменную.

Переносить вызовы автомобильного SDK в FT буквально нельзя: FT работает на другой стороне соединения.

### Интерпретация

Если установленная прошивка следует той же логике SDK, она могла считать группу существующей и отвечать запросом IP вместо повторного включения обнаружения. Это согласуется с тем, что после локальной отмены группа отсутствует и машина перестаёт появляться в peers.

Ограничения:

- Машина может запрашивать IP по иной логике, чем исторический SDK.
- Запрос IP сам по себе не показывает, с каким устройством или группой связано внутреннее состояние магнитолы.
- Наблюдение относится к восстановлению после первого таймаута и не объясняет автоматически исходный отказ 11:44.
- Из телефонных журналов нельзя установить, был ли в этот момент активен CarPlay и когда магнитола освободила свой радиоинтерфейс.

## Что удалось проверить по статусам

[ServiceTypes.kt](https://github.com/fgrcwp/apollo-DuerOS/blob/fddb0be12a24b501bee435a56be3f564a158fd39/CarLife-Android-Vehicle-V2.0/carlife-sdk/src/main/java/com/baidu/carlife/sdk/internal/protocol/ServiceTypes.kt) определяет `MSG_WIRELESS_MD_STATUS = 0x00100008` и `MSG_WIRELESS_HU_STATUS = 0x00108009`. В [CarlifeWirlessStatusProto.proto](https://github.com/fgrcwp/apollo-DuerOS/blob/fddb0be12a24b501bee435a56be3f564a158fd39/CarLife-Android-Vehicle-V2.0/carlife-sdk/src/main/proto/CarlifeWirlessStatusProto.proto) есть только `required int32 status = 1`, без перечисления значений.

Изученный обработчик MD_STATUS передаёт число наблюдателям, а не выполняет встроенный сброс P2P. Назначать неизвестному числу смысл «отключить старое устройство» или отправлять его наугад оснований нет. В просмотренном `ft.log` за 7 ноября записей `car wireless status` нет; это не доказательство отсутствия таких сообщений во всех версиях прошивки.

## Следствия для FT

- Повторный обмен Bluetooth, получение свежего имени, отмена зависших переговоров и подтверждение очистки уже реализованы и выполнялись в проблемной попытке. Предлагать их повторно как новое исправление недостаточно.
- Обязательное ожидание `peerOwner=true` не обосновано: успешное подключение 12:15 началось при `false`.
- Одно увеличение таймаута не устраняет возможное рассогласование состояний.
- Следующая полезная диагностика — явно сопоставлять `HU_IP_REQUEST` с локальными стадиями группы/IP и временем после отмены, сохраняя факт запроса отдельно от пользовательского текста. Существующий лог уже позволил увидеть этот случай.
- Для выбора восстановления со стороны HU нужен подтверждённый механизм конкретной прошивки либо документация OEM. Отдельной команды переключения CarPlay → CarLife в изученных материалах не найдено.
- Исправление A2DP в 3.9.65 относится к повторным обрывам аудиопрофиля после подключения; оно не считается доказанным исправлением этого начального отказа.

При повторении достаточно сохранить отчёт до перезапуска приложения и отметить время, выбранный режим магнитолы и наличие соединения с iPhone. Специальная поездка для текущего документального исследования не требовалась.

## Подготовленные изменения FT

- Каждый `HU_IP_REQUEST` отдельно записывает номер Bluetooth-обмена, наличие локального IP и состояние CMD-канала. Если IP отсутствует и CMD ещё не подключён, сервис дополнительно фиксирует принятую группу, стадию peer/подключения и подготовку повтора, затем запрашивает текущее состояние P2P без отмены переговоров.
- Обработка отложенного события проверяет поколение Bluetooth, номер обмена и экземпляр `CarFinder`. Событие от прежнего соединения или уже восстановленного обмена отбрасывается.
- Используется существующее ограниченное восстановление: четыре запроса имени и однократное повторное открытие Bluetooth спустя 37 секунд отсутствия peer. Появление peer, активные переговоры, принятая группа, подготовка повтора, готовый IP, CMD или проекция не позволяют этому пути разорвать Bluetooth.
- Если к исчерпанию этих попыток машина запрашивала IP, а локальный адрес так и не появился, в текущем шаге поиска машины или Wi-Fi Direct отображается подсказка заново открыть CarLife на магнитоле. Отключение CarPlay предлагается только при его активности. Подсказка снимается при подключении группы, продвижении сессии, ручном повторе или остановке режима.
- Пустой IP и неизвестные команды сброса магнитолы не отправляются. Лимиты и интервалы существующего восстановления не изменены.

Это изменение улучшает диагностику и объясняет пользователю следующий шаг после безуспешного восстановления. Оно не доказывает устранение исходного зависания автомобильной стороны или влияние CarPlay. Для такого вывода нужен следующий реальный случай с журналом либо подтверждённый механизм восстановления OEM.
